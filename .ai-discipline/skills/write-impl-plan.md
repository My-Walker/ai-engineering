# 实现计划

产出可确认的实现计划（对话交付为主）。**不是** OpenSpec/`to-spec` 规格链，不强制落仓。

## 进入条件

- `rule:clarify-gate` 已放行（影响行为的未决已关）。
- SOP 标明需要计划，或改动面大/多路径，或用户要求书面计划。

## 核心规则

1. **先问是否需要书面计划**：约 ≥3 源文件、跨层、多实现路径 → 建议出计划；小改可经用户同意跳过，交付须注明「已跳过计划」。
2. **计划未确认前不得写实现代码**（含「先写一点试试」）。
3. **字段完整**：见下；缺关键字段不算可确认计划。
4. **未经用户要求，不把 Plan 擅自写成项目文件**；用户要求落盘时再确认路径。

## 做法

1. 判断：出计划 / 建议跳过（选项+推荐）。
2. 若出计划，至少包含：
   - **目标**：做成什么、不做了什么
   - **受影响路径**：文件/模块列表（可估）
   - **步骤顺序**：实现与验证顺序
   - **关键取舍**：已选方案与弃选及理由
   - **验收点**：如何判定完成
   - **风险/回滚**：若相关
3. 等人确认或修订；确认后交回 SOP（`skill:tdd` / `skill:implement-change` / `skill:apply-fix` 等）。

## 完成标准

- 用户已确认计划，或明确跳过并已注明；且
- 确认前未开始实现写码。

## 禁止

- 用计划正文绕过澄清门未决。
- 引入 issue 拆票/多 agent 编排作为本 skill 必经步骤。
