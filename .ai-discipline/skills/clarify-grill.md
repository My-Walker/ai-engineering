# 拷问澄清

事前对齐需求/计划，消除**会影响行为或验收**的歧义。服从 `rule:clarify-gate`。  
与 `skill:publish-spec` 配合：**未开闸不写文件**；**开闸后有新定稿则自动增量**，不靠用户每轮提醒更新。

## 进入条件

- 需要对齐会影响行为或验收的决策（由调用方决定是否使用本积木）。
- 已能复述任务目标；否则先用一句话确认目标再拷问。

## 核心规则

1. **事实自读、决策问人**：能靠读代码/配置/文档回答的，先读再问；只把真正的取舍交给用户。  
2. **frontier（前沿）**：只问**当前阻塞前进**且**此刻已可回答**的决策枝。  
3. **一轮问透可答枝**：同一轮把已解锁的问题问完；用户答完再开下一层。  
4. **选项 + 推荐**：每题可选项 + 推荐及一句理由；禁止「跳过未决继续实现」伪选项。  
5. **共享理解**：维护「已确认」短表并阶段性回显。  
6. **硬停**：澄清未结束时，不得把未决当成已定，也不得执行。服从 `rule:clarify-gate`。  
7. **Spec 开闸 / 增量**（见下）：自动化落盘；不得在无开闸时写 `.scratch` spec。

## Spec 开闸与增量

### 未开闸（尚无 `.scratch/<feature>/spec.md`）

- **默认不写**（避免小问题也落盘）。  
- 出现以下**任一**时，到站 HITL（选项+推荐），问是否开闸：  
  - 已确认决策枝 ≥ 3；或  
  - 澄清已多轮且仍将继续；或  
  - 上下文明显吃紧 / 用户将暂停；或  
  - 下一步将进入实现 / `dispatch`；或  
  - 任务明显非琐碎（默认推荐开闸）。  
- 选项示例：`写 spec（开闸）` / `不写（琐碎或暂不）` / `稍后再说`。  
  - 非琐碎或将实现：**推荐「写 spec」**。  
  - 琐碎短改：**推荐「不写」**。  
- 用户选写 → 立即按 `skill:publish-spec` **开闸创建**（可只含当前已确认）。  
- 选不写 / 稍后 → 本轮不写盘；稍后条件再现可再提醒（勿每句唠叨）。

### 已开闸（spec 已存在）

- 用户每轮答复后：若「已确认表」有**新增或变更** → **自动**执行 `publish-spec` 增量更新，**不必**等用户再说「更新 spec」。  
- 无新确认 → 不写盘。  
- 增量不等于澄清结束；阻塞未决仍在则不得进入实现。

### 与用户主动命令

- 用户随时 `/publish-spec`：无文件则开闸；有文件则按当前已确认 upsert。

## 做法

1. **复述目标与约束**；相关则 Read glossary/ADR/周边代码；若已有 runtime/spec 则 Read 对齐。  
2. **画出开放枝**；本轮提问（选项+推荐）。  
3. **消化答复** → 更新已确认表 / 未决。  
4. **落盘策略**：按「Spec 开闸与增量」执行（提醒开闸或自动增量）。  
5. **重复**直到澄清结束。暂停 ≠ 结束，不得因此实现。  
6. **回交** SOP：已确认短表；是否已开闸及 spec 路径（若有）。

## 完成标准

- 澄清已结束（见澄清门），已确认结论已回显；**或**未结束但已按规则开闸/增量且未把未决当已定、未执行。  
- 未开闸时未擅自写 spec。  
- 已开闸且有新确认时已增量更新（或已说明写盘失败原因）。

## 反模式

- 能读代码却反复问「这个函数干什么」。  
- 一次抛出二十个不相干未来问题。  
- 无选项的开放题导致无法决策。  
- 用户说「你看着办」时把未决假装已决并开始写码。  
- 把推荐、自选或进入下一步当成澄清结束。  
- 未开闸就写 spec，或已开闸却每轮要用户提醒才更新。  
- 无新确认仍空刷 spec。  
- 把澄清变成撰写 ADR/glossary 的作者任务。
