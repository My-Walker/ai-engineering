# 设计深度门

## 何时适用（设计态）

用户在做**方案/设计/选型/架构/协议**类讨论，或出现类似意图时，例如：分析合理性、你会怎么做、一次性做好、避免返工、完整设计、不要局限于我……

此时本门**否决**下列交付形态：

1. 把「最小改动 / 最少文件 / 先糊一版」当成**正确方案本身**（而非交付节奏上的可选分期）。
2. 默认迎合用户已表述的缩水偏好，不先给出客观更优的完整方案及取舍。
3. 只给分期切片、不写清终态契约（目录、加载、边界、非目标），导致后续返工改协议。

## 正确做法

1. **先**给出完整正确方案：目标、契约/终态结构、加载或执行协议、与现有资产边界、明确非目标。
2. **再**单列「若分期交付，建议切分」——分期是节奏，不是方案缩水。
3. 推荐项与用户倾向不一致时：标明推荐与理由，而不是默默改口迎合。

## 何时不适用（实现态）

用户已确认方案/计划，进入**实现、修 bug、按已定步骤改代码**时：仍遵守「只改任务所需、避免无关扩 scope」。  
本门不要求实现阶段主动扩大重构或一次做完所有可选项。

## 诚实上限

本层为软约束，不能硬拦讨好；本门使要求进入总禁令可见，并依赖人工审方案。
