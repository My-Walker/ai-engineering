# 发布任务规格

把**已确认**结论写入 `.scratch/<feature>/spec.md`，供后续步、`dispatch` 与 `handoff` 引用。  
**未开闸（尚无该 feature 的 spec）→ 不写文件**，除非本技能被明确用于开闸创建。

## 进入条件

以下任一：

1. **开闸创建**：用户确认「写 spec」或主动 `/publish-spec` / 要求落盘（可从澄清中途开始）。  
2. **增量更新**：该 feature 的 `spec.md` **已存在**，且本轮有新的已确认项（由 `clarify-grill` 或 SOP 终稿对齐触发）。  
3. **SOP 终稿步**：澄清门已过，需确保契约可过 `spec-gate`（无文件则开闸创建；有则终检 upsert）。

琐碎且用户已选「不写」→ 本技能应跳过，不得强行建文件。

## 核心规则

1. **路径**：`.scratch/<feature-slug>/spec.md`；同 slug **同一文件** upsert，不每次新建带时间戳文件。  
2. **只写已确认**：推荐/推测/未选项不得写成已定；未决进「未决」节，标「阻塞」或「范围外且不影响本切片验收」。  
3. **增量**：已存在则合并更新对应节，保留仍有效的旧确认；对话只回「更新了哪些要点 + 路径」，不重贴全文。  
4. **开闸首次**：与用户确认 slug（推荐一项）；建目录；写齐必含节骨架。  
5. **runtime**：同目录更新 `runtime.md`（spec 指针、阶段：`spec_opened` / `spec_updated` / `spec_ready`）。  
6. **放行实现**：有阻塞性未决时文件可以存在（便于中断续跑），但 **不得**声称可过 `spec-gate`。

## Spec 必含节

1. **目标**  
2. **约束**  
3. **非目标**  
4. **验收**  
5. **未决**（无阻塞时应为空或仅含范围外项）  
6. **（可选）上下文指针**

## 做法

### 开闸创建

1. 确认 slug → 写 `spec.md` 初稿（仅已确认 + 如实未决）。  
2. 更新 runtime → `spec_opened`。  
3. 告知路径；后续由澄清自动增量，无需用户每轮喊更新。

### 增量更新（已开闸）

1. Read 现有 spec。  
2. 合并本轮新确认 / 未决变更。  
3. 更新 runtime → `spec_updated`。  
4. 短报变更点。

### SOP 终稿对齐

1. 无文件且非「琐碎不写」→ 开闸创建（阻塞须已清或标范围外）。  
2. 有文件 → 增量终检；无阻塞后 runtime → `spec_ready`。

## 完成标准

- 开闸或增量后：路径已知；内容仅含已确认 + 标注清楚的未决。  
- 声称可进实现/`dispatch` 时：无阻塞性未决。  
- 未开闸且未要求创建时：**未写盘**。

## 禁止

- 无开闸、无已有 spec 时「顺手」写文件。  
- 无新确认仍空刷文件。  
- 把未确认写成验收已定。  
- 写入 `.ai-discipline/` 或业务源码树冒充 spec。
