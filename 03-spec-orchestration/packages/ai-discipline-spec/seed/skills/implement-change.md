# 实现改动

用于 **功能开发**写码（`sop:feature`）。缺陷修复用 `skill:apply-fix`。

## 进入条件

- `rule:clarify-gate` 已放行；影响行为的未决已关。
- 若走过 `skill:write-impl-plan`：计划已确认，或用户明确跳过并已注明。
- 任务类型是新增/扩展能力，不是「只修已有错误行为」（后者走 bugfix）。

## 核心规则

1. **实现已 settled 的工作**：不重新打开产品设计辩论；发现新的行为未决 → 停回 `skill:clarify-grill` / 澄清门。
2. **范围**：仅已确认计划或对话范围；不做范围外重构。
3. **TDD**：若 SOP 本步前要求或用户要求测试先行，先完成 `skill:tdd` 约定缝的红灯再写最少实现。
4. **验证节奏**：实现过程中按需跑相关测试/类型检查；收尾交给 `skill:verify`（可含更全检查）。
5. **不自动 commit / 关单 / 开 PR**。

## 做法

1. 重申范围与验收点（及计划条目，若有）。
2. 按现有代码风格实现；公共行为优先有测试覆盖（见 `skill:tdd` 规则）。
3. 保持增量可运行；避免无关文件大冲洗。
4. 完成后进入 SOP 的 `skill:verify`。

## 完成标准

- 实现落在已确认范围内；关键验收点有对应代码路径。
- 未夹带未授权重构或第二需求。
- 已准备好接受 `skill:verify`（命令或说明已知）。

## 禁止

- 「边写边重新设计」且不回头澄清。
- 把 issue tracker / 多 worktree 编排当成本 skill 前置条件。
