# 缺陷诊断

本 skill **只负责定因**，不选择修复范围、不写长期修复方案。服从 `rule:evidence-gate`。  
若仓内已有相关领域文档/ADR，可 Read 对齐模块心智模型；**不**在本 skill 内新建记忆层资产。

## 进入条件

- 当前在 `sop:bugfix` 的诊断阶段，或用户明确要求诊断/调试报错、错误行为、性能退化。
- 期望 vs 实际行为尚不清楚时，先写清再动手。

## 核心规则

1. **反馈环优先**：必须先有针对**本 bug 同一症状**的 red-capable 信号。没有环，不得给出「已确认原因」，更不得猜改。
2. **已跑过才算环**：能点名**一条已实际跑过至少一次**的命令/测试/脚本，并出示（脱敏后的）调用与输出。
3. **先复现再假设**：未跑通复现（或未收到人工回传证据）前，不进入定因收口。
4. **一次一变量**：最小化与探针时，每次只改一项并重跑环。
5. **可证伪**：候选 3～5 个，每个写「若成立，环上应看到什么」；先列全再逐个测，避免锚定第一个念头。
6. **脱敏**：命令/输出/抓包涂改密钥；凭证留在环境变量；不够用就明说并问用户。
7. **证据不足**：列出已尝试 → 转 `skill:add-logs` / HITL；禁止无环编故事。

## 做法

### 1. 写清症状

期望行为、实际行为、影响范围、首次出现线索（若已知）。确认后续环打的是**用户描述的同一失败模式**，不是邻近的另一个错。

### 2. 建立并收紧反馈环

按环境选用（不绑死某一工具），大致优先序：

1. 能碰到 bug 的失败测试（单测/集成/e2e）
2. 对运行中服务的 curl / HTTP 脚本
3. CLI + fixture，对比 stdout/快照
4. 无头浏览器脚本（若项目已有且必要）
5. 回放已保存请求/事件到隔离路径
6. 最小 harness（单函数/单服务 + 边界 mock）
7. 偶发错误：提高复现率（循环/加压/钉时间种子），目标是可调试的复现率而非 100% 洁癖
8. 已知好坏版本/配置：差分同一输入
9. 性能：profiler / 计量，优于淹没式日志
10. 最后：结构化 HITL（步骤 + 回传格式）

有环之后**收紧**：更快、信号更尖（断言具体症状而非「没崩」）、更确定（钉时间/随机/隔离 IO）。  
30 秒且 flaky 的环几乎等于没环。

**确实建不出环时**：停；列已尝试；向用户要环境权限、脱敏产物（日志/HAR/录屏时间戳）或临时探针许可。**不要**无环进入假设阶段。

### 3. 复现并最小化

跑环至红；确认失败模式与用户一致。  
逐项删输入/步骤/配置并重跑，直到剩下的每一项都承重（再删则变绿）。最小复现既缩小假设空间，也可作日后回归。

### 4. 列假设并证伪

写下 3～5 个假设（可短排序）。用环、日志、断点、测量**一次验证一个**预测；记录已排除与仍开放项。

### 5. 收口

写下**已确认原因 + 证据**（复现命令/日志片段/测试名）；或「无法定因 + 缺什么证据」并停在取证分支。  
定因之后改码范围交给 `choose-fix-scope` / `apply-fix`，本 skill 结束。

## 完成标准（检查清单）

- [ ] 存在已跑过的 red-capable 命令/测试（或等价人工回传证据）
- [ ] 失败模式与用户症状一致；已最小化或说明为何不能再缩
- [ ] 有「已确认原因 + 证据」，或明确转 `add-logs`/HITL
- [ ] 未在无证据时改缺陷业务逻辑

## 反模式

- 盯着代码「看起来像」就改；无环先写长篇根因故事。
- 一次加大量日志/改多处，分不清信号来源。
- 把别的 bug 的绿测当成对本症状的反馈环。
- 「断言没崩」却抓不住用户说的那个症状。
