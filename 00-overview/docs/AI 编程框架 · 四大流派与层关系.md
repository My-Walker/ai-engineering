# AI 编程框架 · 四大流派与层关系

本文管两件事：

1. **流派**：框架与人的权责关系（信谁多一点）。
2. **层 × 流派**：工具落在哪一层、属于哪一派（交叉表）。

**层谱本身**以 [`AI 编程框架 · 通用层.md`](./AI%20编程框架%20·%20通用层.md) 为唯一真源；本文不另维护更短的层列表。  
**日常装多少**见 [`AI 编程框架 · 完备集.md`](./AI%20编程框架%20·%20完备集.md)。

---

## 1. 层 ≠ 流派

| | 层（Layer） | 流派（School） |
| :--- | :--- | :--- |
| 问题 | 在开发流程哪一段发力？ | 人机权责如何分配？ |
| 性质 | 功能定位，可并列 | 价值判断，取向不同 |
| 选型顺序 | **先看层**（痛点在哪） | **再看流派**（愿意让渡多少判断权） |

一句话：**层是「缺什么补什么」，流派是「信谁多一点」。**  
若按流派组织却用层来命名，就会出现「GSD 为什么不在规格沉淀里」这类错位：GSD 在**上下文层**，不是规格沉淀流派本身。

---

## 2. 四大流派（权责）

核心区别：**谁来承担「记住流程、保证质量」的责任。**

命名对照：外文材料里的「战术工具箱 / 工程流程强化 / 规格沉淀强化 / 多角色编排」，与下文「人控派 / 流程接管派 / 文档接管派 / 团队模拟派」同一套划分。

### 2.1 人控派（战术工具箱）

**代表：** [mattpocock/skills](https://github.com/mattpocock/skills)

**主张：** 人类在控制平面，AI 在执行平面。只提供原子宏命令（如 `/tdd`、`/diagnosing-bugs`），**不接管主控制流**。用完即止，token 低、上下文污染小。

**代价：** 完全被动。不敲命令就没有纪律；强依赖工程师判断力；难靠它单独解决多模块状态管理。

### 2.2 流程接管派（工程流程强化型）

**代表：** [obra/superpowers](https://github.com/obra/superpowers)

**主张：** 用硬编码线性流程约束 AI（如 Brainstorm → Plan → TDD → Review），上一步未完不得进入下一步。

**代价：** 上下文消耗高；流程成本与任务规模常不匹配；小任务也被拉长。极端形态见第 4 节。

### 2.3 文档接管派（规格沉淀强化型）

**代表：** [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)、[mindfold-ai/Trellis](https://github.com/mindfold-ai/Trellis)

**主张：** 把持久知识沉成结构化文件（Spec、Delta Spec、决策/规则等），让 AI 基于版本化文档工作，而不是依赖会褪色的聊天记忆。

**代价：** 团队要会写、会维护文档；若缺测试等纪律，规范易流于形式。  
注意：OpenSpec 更偏**规格层**；Trellis 更偏**项目记忆层**——同属文档接管派，但层不同。

### 2.4 团队模拟派（多角色编排型）

**代表：** [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)、oh-my-claude 系（原仓已归档，可参考社区活跃分支）

**主张：** 用多专业化 Agent（PM、架构师、开发者等）通信协作推进项目。

**代价：** 系统复杂度与 token 成本最高；人往往变成虚拟团队的调度员。极端形态见第 4 节。

### 2.5 一句话记住四者

**人控派**把判断权留给你；**流程接管派**用强制顺序替你判断；**文档接管派**用文档资产替你记忆；**团队模拟派**用虚拟团队替你分工。

## 3. 层 × 流派交叉表

层轴与通用层文档对齐。宿主是底座；验证与门禁为横切能力（默认可嵌执行纪律）。

| 层 \ 流派 | 人控派 | 流程接管派 | 文档接管派 | 团队模拟派 |
| :--- | :--- | :--- | :--- | :--- |
| **0. 宿主** | IDE / MCP / 命令（各派共用） | 同左 | 同左 | 同左 |
| **1. 规格层** | — | — | OpenSpec、Spec-Kit | — |
| **2. 上下文层** | 短会话 / handoff 习惯 | GSD 等 | Conductor 一类（偏持久化上下文资产时） | — |
| **3. 执行纪律层** | mattpocock/skills | Superpowers | — | — |
| **※ 验证与门禁** | 命令内硬停；人审 | 流程状态机门 | 写入/归档门闩 | 角色交接仪式中的门（成本高） |
| **4. 项目记忆层** | 手写 pitfalls 笔记 | — | Trellis、记忆 MCP | — |
| **5. 编排层** | — | — | — | BMAD、oh-my-claude、MetaGPT |

### 常见错位澄清

- **GSD 为何不在「规格沉淀」？** 它在上下文层，目标是干净执行窗口，不是沉淀可追溯规格资产。
- **OpenSpec 与 Spec-Kit？** 同层同派；OpenSpec 更轻、偏棕地增量；Spec-Kit 更重、偏绿地全流程。
- **Trellis 为何算项目记忆？** 把规格/任务/规则持久化到仓库供多 Agent 共用，是记忆层特征，不止规格层。
- **oh-my-claude 与 BMAD？** 同属编排层、团队模拟派；BMAD 偏流程仪式，oh-my-claude 偏角色通信。

## 4. 反面参考：走到极致时的代价

不是「设计无价值」，而是**方向做对、日常代价常超过收益**的极端样本。

**Superpowers：** 启动即征税（有报告称会话启动灌入约 22k token）；子代理评审可出现无界棘轮（任务难以宣布 CLEAN）。警示：**强制纪律若不设收敛边界，会从质量控制退化成 token 黑洞。**

**BMAD：** 单步分析即可烧掉大量 token；流程拆成多会话时重复加载材料。警示：**模拟团队若不解决流程断裂，角色分工只会放大上下文浪费。**

二者都是「明确知道自己在为什么付费」之后才值得考虑的选项，不宜作为日常默认。

## 5. 选型口诀（轻量日常）

1. 先看痛点落在通用层的哪一层。  
2. 再看愿意让渡多少判断权（流派）。  
3. 日常优先 **人控派纪律 + 按需的文档接管（规格或记忆）**；流程接管与团队模拟避免常驻。  

一种常见轻量默认（仅作参考，装机厚度见完备集）：

- 执行纪律：skills（人控派）  
- 需要变更契约时：OpenSpec（规格层、文档接管派）  
- 按阶段临时借：GSD / Spec-Kit / Trellis / BMAD 等  

避免：拿 Superpowers 改一个变量名；用纯 skills 硬扛五十人团队协作。
