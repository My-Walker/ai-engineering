# AI 编程框架 · 设计准则

本篇汇总**可追加的体系级准则**（不一条一文档）。  
选型细节见通用层 / 流派 / 完备集；此处只定原则与验收口径。

---

## 1. 协议先于工具

**陈述：** 权威在协议与仓库文件，不在服务进程。Markdown（及约定目录）须能完整表达门禁、流程、记忆治理与交接；人在无 MCP / 专用 CLI / 特定插件时仍可按同一套约定跑通主路径（可更慢）。工具仅负责加速、检索与 API 硬门闩；卸载后流程语义仍可读、可执行。

**分层：** 协议与工件必有；MCP、索引、安装锚点、Hooks 为可选增强。

**验收：** 换宿主或关掉自研服务时，是否只需改挂载方式、而非重写宪法？离开该工具后主路径是否仍能叙述并手工完成？任一为否，说明造厚了，应先撤回协议层。

**反模式：** 协议只活在服务或专有 UI 里；正式知识无法进 git；离开自动灌库就不会记坑。

---

## 2. 外借优先，禁默认造轮子

**陈述：** 引擎类能力（原子 skills、变更规格生命周期、CI、通用检索、成熟编排等）默认**直接使用开源或现成宿主能力**；不新建第二套 OpenSpec / Superpowers / Trellis / BMAD 同类全家桶。自研只允许**薄、可卸载的适配**（门禁语义、记忆治理协议、挂载胶水）。文化与红线用协议表达，不靠再造引擎。

**选用序（必须按序，不得跳步怂恿自研）：**

1. 协议 + md 能否先跑通主路径？  
2. 开源 / 现成工具是否已覆盖引擎部分？→ **直接用**，协议叠在外面。  
3. 差一小块实现且值得回馈社区？→ **提 PR**。  
4. 必须改引擎内部、短期无法合回上游？→ 才考虑 **谨慎 fork**（有合并或退出评估，避免假自研）。  
5. 反复验证「外借叠不住」、且缺口是策略/治理？→ 才 **自研薄层**，并仍遵守准则 1。

**优先级一口径：** 直接用 > 提 PR > fork > 自研薄层。Fork 不是默认项。

**对 Agent / 协作者的硬约束：**

- **禁止**在未走完选用序前，建议「我们自己写一个框架/MCP 全家桶/规范引擎」作为首选方案。  
- **禁止**把「功能更可控」「定制更爽」单独当作自研全家桶的充足理由。  
- 若建议自研或 fork，必须写明：已排除的现成方案、缺口为何叠不住、如何保持人工可运行与可卸载。  
- 默认建议应是：**组装开源 + 补协议/薄门禁**；升格自研须用户明确确认。

**验收：** 新提案是否先给出「直接用哪个开源、差在哪」？若开口即自研引擎，则违规。

**反模式：** 为学习/完美主义重写已有引擎；fork 后大改且无上游路径；用自研平台绑死协议。
