## 1. 三档总览

| 档 | 一句话 | 纪律 | 记忆 | 现场卫生 | 规格 / 硬验证 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **A 个人日常（薄）** | skills + 坑本 | 更碎的按需命令；常驻门禁可无 | 单文件笔记可凑合 | 脏了换会话 | 通常不要 |
| **B 标准最小** | 薄门禁 + 自动 SOP + 正式记忆 | 常驻硬门 + 意图路由 SOP（省心）；侧门少量 `/` | 三目录 + 人审；检索可渐进 | 澄清 → spec；非琐碎 **dispatch**（退化才人手换窗） | 默认不加 |
| **C 成熟日常** | 核心三件套 + 两条加强轨 | 同 B，且命令有完成定义、宜版本化 | 可检索、可治理、可共享 | **一等协议**（spec / dispatch / handoff / 重触发） | **按需轨 D/E** |

推荐阅读：先看第 1 节表 → 默认细读 **B** → 需要再看 A/C 差分 → 附录看「理想重型场景」。

## 2. 档 B · 标准最小完备集（主展开）

### 2.1 定义

**最小完备集 = 执行纪律层（内嵌验证与门禁）+ 项目记忆层。**

宿主始终在；上下文以 **spec + 串行 dispatch** 为主补，人手换窗为退化；多角色编排默认不进。

**完备判据：** 少一层在目标上明显残缺；再加一层多为锦上添花。

**默认目标：**

- 按任务类型干活（答疑、需求分析、新功能、修 bug、重构）——**意图路由自动 SOP**，不靠人背 skill 名组装。
- 坑与决策能记下来，下次少再犯。

### 2.2 总结构

```text
宿主
├─ ① 极薄常驻门禁
├─ ② 自动 SOP（publish-spec + 非琐碎 dispatch）
├─ ③ 项目记忆（md 真源）
└─ ＋ 侧门少量 command（handoff / publish-spec / …）
```

| 积木 | 内容 |
| :--- | :--- |
| **纪律包** | 薄门禁 + SOP 菜谱 + spec/dispatch 积木；command 仅侧门 |
| **记忆** | 可 git 的 md + 检索面（可选 MCP） |

### 2.3 执行纪律

**常驻门禁（约一屏）：** 澄清门、取证门、完成门、路由门；有记忆则加确认门。

**为何极薄且常驻：** 没触发命令时也有底线；长 SOP 常驻会在长讨论后衰减成软建议。

**主路径（省心）：** 自然语言 → 路由 `explore-review` / `feature` / `bugfix` 等 → 跟 steps（含 `publish-spec`、非琐碎 `dispatch`）。  
**侧门 command（示例）：** `/publish-spec`、`/handoff`、`/verify`、`/clarify-grill`…——插入用，不要求人组装 SOP。

Plan/spec 要短（目标 / 约束 / 非目标 / 验收）；琐碎可免写。

**门禁位置：** 嵌在纪律里；升格独立层的时机见通用层文档。

**诚实边界：** 软门禁无法 100% 保证。靠薄常驻 + **spec 真源** + **dispatch 隔离** + 侧门重触发 + 工具/CI 硬点；溜了就重路由或退化换窗。

### 2.4 项目记忆

**收：** `pitfalls/`、`decisions/`、`conventions/`；另备 `handoff.md`、可选 `inbox/`。  
**不收：** 流水账、SOP 全文、个人全局口味（User Rules）。

**协议：** md 真源；索引可重建；写须人审；读用短召回；宁缺毋滥。

**实现档：** A 纯文件 → B + MCP 门闩 → C + FTS/语义。最小集要求「能写、能找回、别太脏」，不强制一上来就上 C。

**与纪律分家：** 纪律管怎么做；记忆管该记住什么。

### 2.5 用 spec + dispatch 补上下文

```text
主会话：澄清 → publish-spec（.scratch/<feature>/spec.md）
       → 非琐碎 dispatch 实现（Task 子代理读 spec）→ join → 验证
退化：  人手新会话 → 读 spec(+handoff) → 实现
收工：  handoff 链 spec；坑/决策人审入库
```

跨切片丢的是聊天过程；不该丢的是 spec 与记忆。没落盘就派发/换窗，丢的是交接。  
**不把「手动组装 Matt skills」写成对等主柱**；需要时可作为个人侧门习惯。

### 2.6 设计理由（摘要）

| 相对 | 态度 |
| :--- | :--- |
| 五层全上 | 只保纪律+记忆；规格/编排后置 |
| 长 SOP 常驻 | 薄门禁 + 按需注入，抗衰减、少固定税 |
| 只 skills | 缺跨会话高信号知识 |
| 只 OpenSpec | 不管任务分型流程，也不专管踩坑库 |

**原则：** 层少而对准目标；常驻只留硬门闩；文件才是跨会话真源；污染贵过漏记；软约束有上限。

### 2.7 检验与升格

**检验：** 任务类型有按需流程；关键硬停在；坑/决策进得了资产；不靠整本 SOP 常驻。

**默认不放：** OpenSpec 全流程、Superpowers 全量启动、BMAD、长常驻百科、自动灌正式记忆、记忆内角色库。

| 痛点 | 升格 |
| :--- | :--- |
| 变更要 propose→apply→archive | 规格层（或直接上档 C 的轨 D） |
| 长期上下文系统性腐烂 | 重型上下文框架 |
| 门禁复制打架 | 独立验证与门禁层 |
| 多角色虚拟团队 | 编排层 |

## 3. 档 A · 个人日常（相对 B 变薄）

**一句话：** 按需 skills + 随手坑本；常驻门禁可极少甚至为零。

| 项 | 档 B | 档 A |
| :--- | :--- | :--- |
| 流程 | 五个正式命令 | 更碎：`/tdd` `/fix` `/ask` 等；`/req` 不必天天完整跑 |
| 常驻门禁 | 4～5 条 | ≤3 或没有 |
| 拆会话 | 推荐习惯 | 小改可同会话 |
| 记忆 | 三目录 + 人审 | `notes/pitfalls.md` 即可 |
| 组合 | 纪律包 + 记忆服务 | skills 为主，记忆用文件凑 |

**为何看起来和 B「没区别」：** 目标仍是纪律+记忆，只是固定成本与治理成本更低。换骨架要等痛点变成审计/编排/系统性上下文腐烂。

**检验：** 常见事能随手触发一种做法；底线有落点；坑找得到；不维护用不上的框架。

## 4. 档 C · 成熟日常（相对 B 加厚）

**口号：** 默认轻、关键时够硬、可长期用、可单独升级。

```text
【天天在】A 纪律  B 记忆  C 现场卫生（一等协议）
【按需开】D 变更规格轨  E 验证加固轨
【默认不开】编排、重型上下文 OS、全量启动灌技能
```

**装机：** 纪律包 + 记忆（MCP 或同等）+ 现场卫生短协议 + 可选 D/E。

### 相对 B 多出来的成熟属性

1. **现场卫生成协议：** 澄清必 `publish-spec`（或声明琐碎免写）；非琐碎优先 SOP **dispatch**；人手换窗为退化；阶段重触发；收工更新 runtime/handoff（链 spec）。  
2. **轨 D：** 跨模块/接口/要留痕时走 OpenSpec 或「结论+验收+归档」；琐碎改不动。规格=改什么，自动 SOP=怎么干。  
3. **轨 E：** CI、写入 API 无确认即拒等硬点；与软门禁分层。

**记忆**默认按可检索、可治理、可共享要求，而不是单文件凑合。

**天天用法示意：**

```text
fetch 记忆 → 点名命令
非琐碎：澄清 → spec → dispatch 实现 → join → 检查（E 兜底；信号则 D）
收工：handoff（链 spec）→ 坑/决策人审入库
```

**再往上升级：** 系统性上下文腐烂 → 重型上下文；多角色组织 → 编排；门禁要审计 → 独立门禁层；组织强制变更规格 → 把 D 提成非琐碎默认。

## 5. 附录 · 理想场景组合（重型视角）

以下**不考虑日常轻量化**，按项目类型搭「最完备」组合——与日常三档是不同哲学。选重型前先看流派文档第 4 节代价。

### 场景一：绿地（边界清晰）

**Spec-Kit（规格）+ Superpowers（执行纪律）**  
蓝图门控 + 强制施工质检。适合中等团队启动。

### 场景二：棕地增量

**OpenSpec（规格）+ skills（执行纪律）**  
Delta Spec 做变更手术刀；skills 点状按需。适合 1～2 人维护存量。

### 场景三：大型复杂、角色多

**BMAD（编排）+ Spec-Kit（规格）**  
虚拟研发组织 + 规格作单一事实来源。适合 10+ 人或强角色化流程。注意 token 与仪式成本。

### 场景四：长期演进、上下文漂移

**Conductor 一类（上下文）+ 编排工具**  
上下文固化为仓库资产，再其上跑多 Agent。适合长期多人/多 Agent 并行。

**总结：** 理想视角是「为当前项目主要矛盾在对应层部署专业工具」；日常视角是「先轻后加」。二者不要混成一个默认装机单。

## 6. 收束

| 你要… | 选 |
| :--- | :--- |
| 自己随便写写、少维护 | **档 A** |
| 有流程感、要记坑、仍保持最小 | **档 B（默认细读）** |
| 天天用、可升级、要规格/CI 标准轨 | **档 C** |
| 某类项目上最全工程仪式 | **附录场景**（并清醒付费） |

说白了：日常完备集都是 **纪律 + 记忆** 同骨架上的厚度选择；成熟档多协议与加强轨；理想场景才把规格/编排/重型上下文拉满。
